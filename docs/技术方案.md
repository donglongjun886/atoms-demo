# Atoms-Demo 技术方案

> 按 to-spec 流程产出。需求侧以 `docs/需求文档.md` 为准，术语以 `GLOSSARY.md` 为准；本文档聚焦实现决策与测试决策。

## Problem Statement

笔试评委需要在约 10 分钟内验证：这是一个“多人 + 多 Agent 团队在同一个共创空间中，通过对话完成需求分析、架构设计、代码生成、测试与应用预览”的可运行 Demo——每个按钮可点、每个状态有反馈、刷新不丢数据、演示流程可复现，且代码能看出清晰的工程分层。

## Solution

一个纯前端 SPA：本地 Mock 引擎驱动完整的共创流程演示，数据持久化在 localStorage，部署到 GitHub Pages。差异化记忆点是 Agent 团队分工与 Workflow 阶段流转的全程可视化；工程分层（engine 状态机 + 可插拔 LLM Provider）为后续接入真实 LLM Workflow 预留骨架。

## User Stories

**账号与项目**

1. As a 访客，I want 用预设 Demo 账号一键登录，so that 零成本开始体验。
2. As a 访客，I want 用昵称/邮箱/密码注册并自动登录，so that 体验完整注册流程。
3. As a 成员，I want 刷新页面后保持登录，so that 演示不被意外登出打断。
4. As a 成员，I want 退出登录后数据全部保留，so that 我可以切号演示多人协作。
5. As a 成员，I want 创建项目（名称 + 可选描述），so that 开启一次共创。
6. As a 成员，I want 项目列表分“我的项目/参与的项目”并显示协作人数与阶段标签，so that 一眼看清项目状态。

**邀请**

7. As a 项目所有者，I want 在邀请面板勾选一个或多个用户发出邀请，so that 组建团队。
8. As a 被邀请人，I want 登录后在项目列表顶部看到邀请通知卡片，so that 知道有人邀请我。
9. As a 被邀请人，I want 接受邀请后项目出现在“参与的项目”且协作者栏出现我的头像，so that 我正式加入共创。
10. As a 被邀请人，I want 接受前对项目不可见不可发言，so that 权限逻辑不穿帮。
11. As a 被邀请人，I want 拒绝后卡片消失且可被再次邀请，so that 演示可以重走邀请流程。
12. As a 成员，I want 有人接受邀请时聊天流出现入群消息，so that 协作有真实感。

**消息流**

13. As a 成员，I want 在群聊中发消息并看到带颜色头像的消息流，so that 区分不同参与者。
14. As a 成员，I want 事件触发确定性的自动回复（入群、阶段交接），so that 每次演示结果可复现。
15. As a 成员，I want 同一事件多次触发时话术按序轮换，so that 重复演示不像复读机。
16. As a 成员，I want 消息逐条延迟出现，so that 对话有节奏感而非瞬间刷屏。

**Workflow**

17. As a 成员，I want 在顶部阶段条看到六个阶段与当前阶段高亮，so that 知道流程走到哪里。
18. As a 成员，I want 看到负责当前阶段的 Agent 显示“工作中”，so that 感知 Agent 团队在分工。
19. As a 成员，I want 需求分析阶段 Mike 用问题卡一次澄清我的需求（单卡片 3 题），so that 方案建立在对齐的理解上。
20. As a 成员，I want 方案以计划卡呈现并可批准/拒绝，so that 我掌控流程推进。
21. As a 成员，I want 在聊天里用自然语言（如“开始构建”）推进流程，so that 体验对话驱动的叙事。
22. As a 成员，I want Agent 执行时看到活动卡（如“已处理 N 个步骤”），so that 工作过程不是黑盒。
23. As a 成员，I want 构建阶段看到架构图模块逐个变色、代码文件同步出现，so that 直观看到“应用在长出来”。
24. As a 成员，I want 测试阶段 Alex 报出各模块覆盖率，so that 流程有完整的收尾。
25. As a 成员，I want 构建动画可重播，so that 可以给不同评委重复演示。

**代码与预览**

26. As a 评委，I want 代码面板的内容与预览应用的功能一一对应，so that 演示不自相矛盾。
27. As a 评委，I want 预览里的任务管理应用可添加/勾选/筛选/删除，so that 确认这是真实可交互的产物。

**方案共编**

28. As a 成员，I want 编辑方案 Markdown 并保存，so that 参与共创。
29. As a 成员，I want 修改记录按用户颜色留痕，so that 看到谁改过方案。
30. As a 成员，I want 在方案下方评论区讨论，so that 围绕产物交流。

**持久化**

31. As a 评委，I want 刷新页面后项目/消息/方案/Workflow 状态都在，so that 确认数据持久化真实存在。
32. As a 演示者，I want 清除浏览器数据即可重置全部状态，so that 可以干净地重新演示。

## Implementation Decisions

**技术栈**：Vite + React 18 + TypeScript + Tailwind CSS v3 + shadcn/ui（锁定 Tailwind v3，组件手动复制最小集：button/card/tabs/input/dialog/avatar，不走完整 CLI 工作流）；React Router 使用 HashRouter（GitHub Pages 无 SPA 回退）；Zustand + `persist` 中间件做状态与 localStorage 持久化，当前会话用户 ID 也持久化以支持刷新保持登录，登出仅清除该字段。所有 persist store 配置 `version`，migrate 直接回退种子态；`onRehydrateStorage` 捕获解析失败，数据损坏时回退种子态。

**分层与模块**：

- **engine 层**（纯逻辑，唯一测试接缝）：
  - Workflow 状态机：六阶段（需求分析 → 方案确认 → 架构设计 → 代码生成 → 测试 → 预览），定义合法转移与各阶段可用动作；对话指令经意图匹配后驱动同一状态机，与按钮入口无二义性。**计划卡拒绝（Decline）→ 返回需求分析阶段**，Emma 以确定性话术重出方案，同一项目最多拒绝 2 次，第 2 次拒绝后话术引导批准。**未匹配任何意图的自由输入 → 兜底回复**：由当前阶段负责的 Agent 应答并提示当前可用指令。
  - 邀请状态机：纯函数 `transition(invitation, action)`，两条不变式（接受前被邀请人对项目不可见；拒绝不记黑名单）在该函数内强制；store 只做调用与持久化包装。
  - 对话脚本：事件 → 消息序列，每事件 2 套话术按触发次数轮转；消息带逐条延迟节奏。
  - Agent 团队定义：Mike/Emma/Bob/Alex 的角色、头像颜色、台词风格，对齐官方阵容。
- **llm 层**：Provider 接口（输入上下文，输出消息/动作序列），默认 MockProvider 读 engine 脚本。本期**仅交付接口定义 + MockProvider**；OpenAI 兼容 Provider 实现与 API Key 设置界面不做（列入 Out of Scope）。
- **store 层**：users、projects、workflow 三个 store；领域实体为 User、Project、Member、Invitation（待处理/已接受/已拒绝）、Message、PlanEdit、PlanComment、WorkflowState。**首次启动（persist 为空）时注入种子数据（5 个预设 Demo 账号等）**，这是 US 1 与 US 32 的共同前提。
- **UI 层**：登录页（Demo 账号卡/登录/注册三 tab + “重置 Demo 数据”入口：清 key 并重新播种）、项目列表页（含邀请通知卡）、共创空间（左聊天活动流 + 右 App Viewer 标签页：方案/架构图/代码/预览 + 顶部阶段条与协作者栏）。**共创空间路由入口校验当前用户是否为项目成员**，否则重定向回项目列表（邀请不变式的第二道防线，防 URL 直达）。

**关键交互实现**：

- 构建动画：状态机驱动的时间线编排（模块状态：等待 → 构建中 → 完成），约 10 秒，支持重播；代码文件出现顺序与架构图模块一致。**重播 = 仅 UI 层回放动画**，不改 WorkflowState、不追加消息、不消耗话术轮转。**动画进行态不落盘**（状态机只持久化稳定阶段），中途刷新恢复时回到“代码生成”入口待触发。
- 预览应用独立为 `src/preview-app/`；代码面板用 Vite 的 `?raw` import 直接读取预览应用的真实源码字符串渲染——天然自洽、零同步成本，禁止手工维护两份。预览应用的任务数据随项目持久化（US 31）。
- 消息在事件触发时**一次性全部写入 store**（即时持久化），逐条延迟仅是 UI 渲染队列的呈现节奏；刷新后全部可见，确定性不受影响。
- 邀请状态机的两条不变式在 engine 纯函数内强制（见上），路由守卫在 UI 层兜底。

**部署**：GitHub Pages；Vite 配置 `base` 为仓库名路径；用 GitHub Actions 在 push 到 main 时构建发布。

## Testing Decisions

**接缝**：唯一测试接缝是 `engine` 纯逻辑层（最高层、不碰 DOM）。Vitest 单测覆盖：Workflow 合法/非法转移（含 Decline 回退与次数上限）、邀请状态机不变式、话术语轮转的确定性、兜底回复。

**好测试的标准**：只测外部可观察行为（给定事件与状态，断言转移结果与消息序列），不测内部实现细节。

**UI 验收**：不引入 Playwright 等组件/E2E 设施。验收路径为 spec 第 8 节的演示脚本，由 **Kimi Work 浏览器插件**对部署后的 Pages 链接执行；同时将演示脚本转成一份**人工走查 checklist** 作为外部工具不可用时的降级预案。新仓库无测试先例；首个测试文件即建立风格。

## Out of Scope

实时共同编辑与多设备同步；角色权限细分；应用版本历史与回滚；多类型应用生成；真实部署生成物；选区批注与模块评论区；真实 LLM 调用（默认 Mock，本期仅交付 Provider 接口 + MockProvider，OpenAI Provider 实现与 API Key 设置界面不做）；多标签页数据同步（假设单标签页）；移动端适配（仅桌面端，最小宽度 1280px）。不渲染任何无功能入口——需展示的后续能力一律不出现，而非置灰。
