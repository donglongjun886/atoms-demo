# Atoms-Demo 需求文档

> 本文档是项目的需求与规格说明（spec），由 grill-with-docs 讨论沉淀而来。术语以根目录 `GLOSSARY.md` 为准，工程约定以 `AGENTS.md` 为准。实现过程中如偏离本文档，先更新本文档再改代码。

## 1. 背景与目标

AI 初创公司笔试项目：参考 [Atoms](https://atoms.dev/) 实现一个可运行的网页应用，演示“智能体驱动应用生成并以可视化网页展示”的能力。要求真实交互、数据持久化、提供在线访问链接与公开源码，评估维度为完成度、工程思维、用户体验、创新性、可交付性。

## 2. 产品定位

多人 + 多 Agent 的 AI 应用共创 Demo：人类成员与角色化的 Agent 团队在同一个共创空间中，通过对话完成需求分析、架构设计、代码生成、测试与应用预览的全流程演示。

**主打亮点**（评委可直接感知）：

1. Agent 团队分工与 Workflow 阶段流转的全程可视化；
2. 多人协作的真实感（邀请、共同编辑、消息流）。

**技术取舍**（非亮点，仅为降低演示门槛的工程选择）：

- 默认 Mock 引擎开箱即跑，无需真实 LLM；架构预留可插拔的 LLM 接入层，支持配置 API Key 切换真实模型。
- 使用浏览器 localStorage 持久化，不引入服务端。

## 3. 用户与角色

### 3.1 人类成员

- 5 个预设 Demo 账号（Alice/Bob/Charlie/Diana/Eve），各有独立颜色与头像，一键登录。
- 支持极简注册（昵称 + 邮箱 + 密码）。密码明文存 localStorage，仅限演示环境，文档中注明。
- 退出登录只清除当前会话，全部数据保留。

### 3.2 Agent 团队

4 个角色化 Agent，名字与分工对齐 Atoms 官方默认阵容（官方无专职测试角色，测试由工程师兼任）：

| Agent | 角色 | 负责阶段 |
|---|---|---|
| Mike | 组长 | 接单、澄清需求（问题卡）、协调交接、收尾总结 |
| Emma | 产品经理 | 需求确认、方案产出（计划卡） |
| Bob | 架构师 | 模块架构图 |
| Alex | 工程师 | 构建动画、代码文件、测试覆盖率报告 |

## 4. 功能需求

### 4.1 账号

- Demo 账号卡片一键登录；注册后自动登录。
- 登录态仅保存在会话中；刷新页面保持登录（会话存 sessionStorage 或持久化但可登出清除，实现时二选一，倾向持久化当前用户 ID 便于刷新恢复）。
- 项目列表页分“我的项目”和“参与的项目”两个区域。

### 4.2 项目

- 创建项目（名称 + 可选描述），创建者成为所有者。
- 项目卡片显示协作人数与当前 Workflow 阶段标签。
- 点击卡片进入共创空间。

### 4.3 邀请

状态机：`待处理 → 已接受 / 已拒绝`。

- 邀请面板中勾选用户并发出邀请；可一次邀请多人。
- 被邀请人登录后，项目列表顶部出现邀请通知卡片（接受 / 拒绝）。
- **接受前**：被邀请人对项目不可见、不可发言。
- **接受后**：出现入群消息、头像进入协作者栏、项目出现在“参与的项目”。
- 拒绝后卡片消失，可再次被邀请；不记录黑名单。

### 4.4 消息流（确定性脚本）

- 群聊模式，消息带发送者颜色与头像；Agent 消息带角色标识。
- 所有自动消息由**事件驱动的确定性脚本**产生：邀请被接受必出现入群消息；阶段推进时对应 Agent 必发言交接。
- 同一事件准备 3–4 套话术，按触发次数轮转（可预测但不复读）。
- 消息逐条延迟出现（300ms–1s），保留节奏感；不做随机触发。

### 4.5 方案共编

- 方案以 Markdown 呈现，可编辑、保存。
- 每次保存追加一条修改记录（谁、时间、操作），按用户颜色标识；不做 diff 对比。
- 方案下方为扁平评论区，评论带用户颜色；不做选区批注。
- 单浏览器切号，无并发编辑，保存即覆盖。

### 4.6 Workflow（主打亮点）

状态机：`需求分析 → 方案确认 → 架构设计 → 代码生成 → 测试 → 预览`。

- **双入口推进**：方案以**计划卡（Plan Card）**形式呈现，带「批准 / 拒绝」按钮（对齐官方交互）；同时支持对话指令触发；两者驱动同一个状态机。
- **需求澄清**：需求分析阶段 Mike 通过**问题卡（Question Card）**逐题反问澄清，用户逐条回答后才产出方案。
- **活动卡（Activity Card）**：Agent 执行时聊天流中出现活动卡（如“已处理 N 个步骤”），让工作过程可见。
- 顶部阶段条：当前阶段高亮，负责 Agent 显示“工作中”状态。
- 阶段切换时，对应 Agent 在聊天流发言交接（如 Emma：“需求已确认，@Bob 接手架构设计”）。
- **代码生成阶段**：模块架构图中的模块按顺序变色（等待 → 构建中 → 完成），右侧代码文件同步逐个出现；全程约 10 秒，可重复触发（“再看一遍”）。
- **测试阶段**：Alex 在构建收尾时报出各模块测试覆盖率。

### 4.7 代码与预览

- 代码面板：展示与预览应用自洽的源码（内容必须与预览可交互的功能一一对应）。
- 预览面板：单个旗舰任务管理应用，真实可交互（添加、勾选、筛选、删除）。
- 预览实现与代码面板展示内容同步维护，禁止“代码随便贴、预览另一套”。

### 4.8 持久化

- 全部数据存 localStorage：用户、项目、成员、邀请、消息、方案、修改记录、评论、Workflow 状态。
- 清除浏览器数据即重置全部状态（文档注明）。

### 4.9 共创空间布局

对齐官方两栏布局：

- **左栏**：聊天 / Agent 活动流（消息、问题卡、计划卡、活动卡都出现在这里）。
- **右栏 App Viewer**：标签页承载 方案 / 架构图 / 代码 / 预览；构建动画在架构图标签内进行，代码生成阶段自动切到代码标签，完成后切到预览标签。
- **顶部**：阶段条 + 协作者栏 + 邀请入口。

## 5. 非目标（本期不做）

- 实时共同编辑、多设备同步；
- 角色权限细分（所有协作者权限相同）；
- 应用版本历史与回滚；
- 多类型应用生成（单模板做精）；
- 真实部署生成物；
- 选区批注、模块评论区；
- 真实 LLM 调用（默认 Mock，预留接入层）。

判断标准：评委在 10 分钟验收里感知不到的能力，不为它写代码。

## 6. 技术方案

- **前端**：Vite + React 18 + TypeScript + Tailwind CSS + shadcn/ui。
- **状态**：Zustand + `persist`（localStorage）；路由 React Router（HashRouter，适配 GitHub Pages）。
- **分层**：

```
src/
├── engine/
│   ├── workflow.ts    # 阶段状态机：当前阶段、可执行动作、转移规则
│   ├── scripts.ts     # 事件 → 消息序列（含多套话术）
│   └── agents.ts      # Agent 团队定义：角色、名字、头像、台词
├── store/             # Zustand stores（user / project / workflow）
├── llm/
│   └── provider.ts    # 可插拔接口：MockProvider / OpenAI 兼容 Provider
└── components/ pages/ ...
```

接真实 LLM 时 workflow 与 UI 原样保留，只替换 Provider 实现。

- **数据模型**（localStorage 内）：User、Project、Member、Invitation（状态机）、Message、PlanEdit、PlanComment、WorkflowState。

## 7. 部署

- GitHub 公开仓库 + GitHub Pages；Vite 配置 `base` 路径，使用 HashRouter。
- Atoms 账号仅用于产品调研，不作为部署或开发路径。

## 8. 演示路径（验收脚本）

### 8.1 三分钟版

1. Alice 一键登录 → 创建项目 → 与产品经理 Agent 对话 → 点击“确认方案”；
2. 观看阶段条推进：架构师出图 → “开始构建” → 工程师构建动画 + 代码逐个出现 → 测试工程师报覆盖率 → 预览可交互任务应用；
3. 邀请 Bob → 登出 → Bob 登录接受邀请 → 发言、编辑方案；
4. 登出 → Alice 登录 → 看到 Bob 的消息、方案修改记录与评论。

### 8.2 验收要点

- 每个按钮可点、每个状态有反馈；
- 刷新页面数据不丢；
- 演示脚本每一步可复现（无随机性导致的缺席消息）；
- 邀请状态机无逻辑穿帮（未接受不可见）。

## 9. 后续规划

核心方向为 **LLM Workflow**：多 Agent 协调（需求/架构/编码/审查）、项目上下文管理、工具调用与质量保障（构建、测试、人工确认、失败重试）。本期的 Mock 引擎分层（workflow 状态机 + 可插拔 Provider）即为其界面与状态骨架。
