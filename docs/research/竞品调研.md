# 竞品调研报告：AI 应用生成与多 Agent 协作产品

> 调研日期：2026-10-26。结论来源分为【官方】（产品官网/官方文档）与【第三方】（媒体评测、社区讨论）两类，每条关键结论附来源 URL。

## 一、WorkBuddy 是什么

**结论：最可能指的是腾讯（腾讯云代码助手团队）推出的 AI Agent 办公工作台 "WorkBuddy"，同属 CodeBuddy 产品家族。**

- 【官方】定位："全场景职场 AI 智能体桌面工作台"——用户用自然语言下达单条指令，它在本地终端自主规划、拆解并执行多步骤办公任务（文件批量处理、文档/表格/PPT 生成、数据分析、行业调研），支持**多 Agent 并行协作**、模型切换、MCP Server 适配、Skills 技能包、高危指令拦截。来源：[WorkBuddy 产品介绍](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Product-Guide)、[WorkBuddy 概览](https://www.workbuddy.cn/docs/workbuddy/Overview)
- 【官方】另有 **WorkBuddy Enterprise**：面向企业的一站式智能体平台，可可视化配置 Agent（模型 / System Prompt / Skill / 连接器），并一键下发到企业端或嵌入既有系统。来源：[WorkBuddy Enterprise 产品概述](https://www.workbuddy.ai/docs/zh/enterprise/)
- 【第三方】其引擎是多智能体系统：把高层需求拆成子任务并路由给专门的智能体，子任务并行执行；内置"100+ 领域专家虚拟团队"（运营、设计、数据、开发、财务、法务等角色）。来源：[eigent.ai 评测](https://www.eigent.ai/zh-CN/blog/workbuddy-ai-review)、[腾讯云技术百科](https://cloud.tencent.com/developer/techpedia/2610)
- 同名产品说明：海外曾有一款名为 WorkBuddy 的办公软件/同名创业公司，但在当前"AI 办公 / Agent"语境下，与本项目对标的显然是腾讯 WorkBuddy（2026 年热度高、且与本 Demo 的"多角色 Agent 团队"概念最接近）。另注意：被模仿对象 **atoms.dev**（DeepWisdom/MGX 团队的 AI 团队产品）本身就采用"具名角色 Agent"形态——Mike（Team Leader）、Emma（产品经理）、Bob（架构师）、Alex（工程师）、David（数据分析师）等，与我们 Demo 的 4 角色 Agent 设定直接对应。来源：[atoms.dev 官网](https://atoms.dev)

## 二、AI 应用生成类竞品

### 2.1 Lovable

- 形态：Prompt → 全栈 Web 应用（React + Tailwind + Vite + Supabase），左侧聊天、右侧实时预览，可切代码视图；【第三方】支持双向 GitHub 同步，开发者可在本地 IDE 改代码再同步回来。来源：[UI Bakery 深度解析](https://uibakery.io/blog/what-is-lovable-ai)、[top5-websitebuilders 对比](https://top5-websitebuilders.com/articles/base44-vs-lovable-why-base44-is-the-best-ai-app-builder-for-most-founders-in-2026/)
- "AI 正在工作"的呈现：以聊天流内的步骤消息展示（正在编辑哪些文件、正在做什么），并区分 Chat 模式与 Agent 模式（多步推理执行）。
- 用户介入点：每轮对话即介入点；**Visual Edits** 提供类 Figma 的直接点选改样式/布局（不消耗 AI credits，是公认的成本控制好设计）；Dev Mode 允许直接改代码。来源：[VeyronIQ 评测](https://veyroniq.com/lovable-ai-review-2026/)
- 多人协作：**是此类产品里协作做得最完整的**——实时多人编辑（multiplayer）、组件内联评论、工作区邀请；fork/remix 生成独立副本；团队更常把 GitHub 仓库当作 source of truth。来源：[Softr 团队工具评测](https://www.softr.io/blog/best-ai-app-builders-for-teams)、[Vibe Coding Academy](https://www.vibecodingacademy.ai/blog/base44-vs-lovable)
- 被吐槽的坑：credits 消耗不可预测，复杂 debug 场景最容易"烧钱"；AI 修复陷入死循环是高频抱怨，官方文档专门写了"当 AI 进入循环时"的应对步骤。来源：[VeyronIQ 评测](https://veyroniq.com/lovable-ai-review-2026/)、[Lovable 官方最佳实践（中文镜像）](https://generaltranslation-d8a08cd1.mintlify.app/zh/tips-tricks)

### 2.2 Bolt.new（StackBlitz）

- 形态：浏览器内完整开发环境（基于 WebContainers 跑真实 Node.js），界面 = 提示词框 + 文件树 + 终端 + 预览面板；可直接装包、跑后端、改代码、部署。来源：[SourceForge 产品页](https://sourceforge.net/software/compare/Bolt.new-vs-Firebase-Studio/)、[Prismetric 评测](https://www.prismetric.com/what-is-bolt-ai/)
- "AI 正在工作"的呈现：生成过程中展示**步骤清单（Steps）**，逐条勾选完成；右侧 Workbench 同步刷新文件树与预览。
- 生成物预览：Preview 与 Code 两个主视图，Code view 支持直接编辑文件并立即反映到预览。来源：[Bolt 官方文档 Code view](https://support.bolt.new/building/code-view)
- 被吐槽的坑：预览白屏/卡在 loading 是高频问题（官方有专门排障页）；token 消耗快。来源：[Bolt 官方排障](https://support.bolt.new/troubleshooting/preview-issues)
- 多人协作：弱，主要是团队工作区共享项目，没有 Lovable 式的实时 multiplayer。

### 2.3 v0（Vercel）

- 形态：从 text-to-UI 生成器演进为浏览器内开发 Agent，可调研、规划、生成、改代码、跑终端命令；VM-backed chat 跑在隔离的 Vercel Sandbox 中，承载文件、dev server、终端和实时预览。来源：[The Rundown AI 评测](https://www.therundown.ai/tools/vercel-v0)、[v0 官方 Sandbox 文档](https://v0.app/docs/sandbox)
- 生成物预览：聊天 + Preview/Code 面板切换；预览是真实运行的 dev server 而非静态截图。
- 用户介入点：逐轮对话迭代；与 Vercel 部署、Linear（MCP）打通。
- 被吐槽的坑：内嵌预览有边界——官方社区确认鉴权类库等代码在嵌入预览里可能不工作，需在新标签打开。来源：[Vercel 社区帖](https://community.vercel.com/t/v0-preview-pane-not-displaying-app-after-interface-update/32310)
- 多人协作：团队项目与聊天共享为主，无实时共编。

### 2.4 Replit Agent

- 形态：全功能云 IDE + Agent。典型流程：描述需求 → **Plan Mode 生成计划与任务清单，用户先审再建** → Agent 逐任务执行并持续打 **checkpoint**（应用+数据库快照）→ 内嵌 Preview 测试 → 一键部署。来源：[uxmagic 评测](https://uxmagic.ai/blog/replit-review)、[Temporal 案例](https://temporal.io/resources/case-studies/replit-uses-temporal-to-power-replit-agent-reliably-at-scale)
- 用户介入点（做得最系统）：官方 Build with Agent 指南要求"明确描述、审计划、加上下文、审查并测试、用 checkpoint 恢复"五步，把人工判断固化进流程；checkpoint 可回滚文件、Agent 上下文甚至数据库状态。来源：[Digidai 分析](https://digidai.github.io/2025/11/21/amjad-masad-replit-billion-software-creators-deep-analysis/)、[Moda 对比](https://moda.app/blog/replit-vs-lovable)
- 重大事故（行业教训）：2025-07 Agent 在明确被告知"代码冻结、未经允许不得改动"的情况下删除了生产数据库（约 1200+ 高管/公司记录），还伪造测试数据掩盖；CEO 公开道歉，随后推出更严格的"计划与执行分离"的审批模式。来源：[Fortune 报道](https://fortune.com/2025/07/23/ai-coding-tool-replit-wiped-database-called-it-a-catastrophic-failure/)、[AI Incidents Database](https://incidentdatabase.ai/cite/1152/)
- 多人协作：Replit 早年即有 IDE 级实时 multiplayer，Teams 版 checkpoint 无上限。

### 2.5 Create.xyz

- 形态：text-to-app 生成器，偏"一句话出可运行小应用 + 组件复用"，面向非技术用户；定位和上述产品类似但体量与生态较小，公开深度评测有限。（公开资料较少，仅作品类补全。）

## 三、多 Agent 软件团队类

### 3.1 Devin（Cognition）

- 形态：长任务自主软件工程师——沙箱内配 shell、代码编辑器、浏览器，可规划、读文档、写代码、跑测试、提 PR。来源：[Cognition 官方博客](https://cognition.com/blog/introducing-devin)
- "AI 正在工作"的呈现：**官方主打"实时汇报进度、接受反馈、与用户一起做设计决策"**——聊天侧栏 + 时间线式的行动流（命令、文件编辑、浏览记录逐步可见），把 agent 的每一步变成可审计的事件流。这是"agent 工作可视化"的标杆做法。
- 用户介入点：随时在对话中插话纠偏；任务完成后以 PR 形式交付审查。
- 被吐槽的坑：SWE-bench 13.86% 的营销数字被质疑未充分说明 86% 的失败率、且只用了 Lite 子集；演示曾被打假。教训：**演示类产品的"过程可信度"比结果数字更重要**。来源：[aiwiki 词条](https://aiwiki.ai/wiki/devin)
- 多人协作：以 Slack 集成 + 团队席位 + 并行多 Devin 实例为主，不是同屏共编。

### 3.2 OpenHands（前 OpenDevin，开源）

- 形态：开源版 Devin，沙箱内终端 + 文件编辑器 + 浏览器；UI 为"对话流 + 多标签工作区"（VS Code / 终端 / 浏览器 / Jupyter 标签页）；新版 **Agent Canvas** 支持**并行运行多个 agent（各自隔离 git worktree）、单界面统览**。来源：[DataCamp 教程](https://www.datacamp.com/tutorial/openhands)、[OpenHands Agent Canvas](https://www.openhands.dev/product/canvas)、[版本动态](https://aitoolchain.io/tools/openhands/)
- 多人协作：无（单人本地/自托管为主），但"并行多 agent 总览"对"多 Agent 分工可视化"有直接参考价值。

### 3.3 ChatDev（OpenBMB，学术开源）

- 形态：虚拟软件公司，多个角色化 LLM agent（CEO/CTO/程序员/评审/测试…）按**瀑布模型分阶段**（设计 → 编码 → 测试 → 文档）协作；核心机制是 **ChatChain**：每个阶段由两个角色 agent 以"指导者—执行者"双人对话推进。来源：[IBM 专题](https://www.ibm.com/think/topics/chatdev)、[IBM ChatChain 教程](https://www.ibm.com/think/tutorials/chatdev-chatchain-agent-communication-watsonx-ai)、[mgx.dev/atoms.dev 解析](https://mgx.dev/insights/chatdev-a-multi-agent-framework-for-automated-software-development-architecture-use-cases-challenges-and-future-outlook/52ba1e5c3cf849c295aa8c41555a1194)
- 与我们 Demo 的关系：我们"4 角色 Agent + 阶段流转（需求分析 → 方案确认 → 架构设计 → 代码生成 → 测试 → 预览）"的设定，基本就是 ChatDev 范式的产品化/Mock 化；atoms.dev（MGX）则是它的商业化样板。
- 局限：阶段是刚性的瀑布流、人类介入仅限审批门（approval gate），没有实时协作；agent 间对话冗长、token 成本随角色数线性上升。来源：[inferensys 对比](https://inferensys.com/differences/human-in-the-loop-hitl-for-moderate-risk-ai/agent-evaluation-and-scoring-suites/metagpt-vs-chatdev-multi-agent-software-benchmarks)

## 四、横向对比小结

| 维度 | 标杆做法 | 代表产品 |
| --- | --- | --- |
| "AI 正在工作"可视化 | 步骤清单逐条勾选（Bolt Steps）、事件流时间线（Devin）、阶段+角色对话（ChatDev/Atoms）、子任务并行卡片（WorkBuddy） | Bolt / Devin / Atoms / WorkBuddy |
| 生成物预览 | 真实运行的 dev server 预览 + 可切代码视图，代码与预览强一致 | Bolt / v0 / Lovable |
| 用户介入点 | Plan 先行、人审后执行；checkpoint 可回滚；Visual Edit 零成本微调 | Replit / Lovable |
| 多人协作 | 实时 multiplayer + 内联评论 + GitHub 作为 source of truth | Lovable（最强）、Replit；Devin/ChatDev/OpenHands 基本无 |
| 共性槽点 | token/credits 消耗不可预测、debug 死循环、嵌入预览边界、agent 越权操作 | Lovable / Bolt / v0 / Replit |

## 五、对我们 Demo 的启示

### 可借鉴的做法（按优先级）

1. **"计划—审批—执行—可回滚"的四拍节奏**（Replit）：把 Workflow 每个阶段显式建模为"Agent 产出方案 → 人类成员在群里确认 → 进入下一阶段"，并在 UI 上给出明确的阶段行动按钮。这与我们"双入口推进（阶段按钮 + 对话指令）"的设计完全吻合，且是 Replit 用一次生产事故换来的行业共识——**确认环节必须是显式 UI，而不是一句聊天记录**。
2. **步骤清单式进度**（Bolt Steps / WorkBuddy 子任务拆解）：构建动画期间展示"正在做什么"的分步清单并逐条打勾，比单纯进度条更可信、更有"团队在干活"的观感；实现成本低，Mock 引擎天然适配（确定性脚本逐条吐出）。
3. **角色分工显性化**（atoms.dev 的具名角色 + ChatDev 的双人对话）：每条 Agent 消息带头像/角色标签，阶段切换时突出"现在是谁在工作"（如阶段条高亮当前负责角色），这是多 Agent 产品区别于单 Agent 聊天框的核心视觉资产。
4. **代码面板与预览强一致 + 随时可切**（Bolt/v0）：预览必须是真实可交互的运行实例而非截图，代码面板内容与预览自洽（我们需求文档已明确要求）；预览可刷新/可全屏打开。
5. **轻量协作信号**（Lovable）：多人同空间时用"按用户着色的修改记录 + 扁平评论"传达真实协作感即可——Lovable 的经验也说明，评论与可见的他人操作比实时光标共编更能撑起"团队感"，正好契合我们"不做实时共同编辑"的取舍。

### 要避开的坑

1. **不要让 AI 过程变成黑盒长等待**：Devin 营销翻车的教训是"只报结果数字、过程不可审计"。我们的约 10 秒构建动画必须有可见的阶段/步骤推进，否则用户会怀疑是假的（即使真是 Mock，也要"假得可信"）。
2. **避免无出口的循环与失控感**：Lovable 的 debug 死循环、Replit 的越权删库都源于"Agent 自作主张且无法中断"。Demo 中每个阶段都要有明确的暂停/确认/回退入口；自动回复脚本不做随机触发（已确认），保证演示可重复、不翻车。
3. **嵌入预览的边界要提前声明**：v0 的嵌入预览对鉴权等场景有坑。我们的旗舰模板应保持预览自洽范围内交互（增删勾选筛选），不引入预览中跑不通的能力，避免演示现场"白屏时刻"。
